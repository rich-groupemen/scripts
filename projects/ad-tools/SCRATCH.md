## Brief capture (from Richard, 2026-10-15) — DRAFT, not final

### 1. Lab environment
- Two VMs mirroring production: (a) **AD** domain controller, (b) **Debian**
  running **LDAP + GLPI**.
- "All users and passwords are shared across logins" — i.e. the same user
  identity/password works for AD and for GLPI/LDAP. **RESOLVED (Round 2):
  GLPI reads AD, so the tool manages AD only.**

### 2. Archive = deactivate, never delete
- Archiving a user means **disabling the account** (`Disable-ADAccount`),
  not deleting it. Reversible by re-enabling.
- Open: does "archive" *also* move the user to an archive OU, or disable
  in place? (Affects the whole menu design.)

### 3. Users and passwords
- Username format: **`name.surname`** (e.g. `richard.pearsall`).
- Password value: **generated by the tool** (Round 2 scheme: French word +
  digits + special, 10 chars). See Round 2.
- Password **changes every 3 months** — domain policy (PSO/GPO); the tool
  does not set expiry and does not configure password policies.
- **No forced change at first logon** → `-ChangePasswordAtLogon $false`.

### 4. Interactive flow (the core spec)
```
Main menu:  [ Add ]   [ Archive ]   [ Modify user ]

Add
 └─ Choose OU:  ( Create new OU )  |  ( Use existing OU → pick from list )
    └─ all subsequent actions happen in that OU
       ├─ New OU          → Create new groups (if required)
       └─ Existing OU     → Create new groups | Create new users
            └─ Create new user   → create user + pick from the OU's
                                    groups to join (checkbox list)

Modify user
 └─ change the groups a user belongs to
```
- Group creation includes no "permissions" configuration (removed).

### 5. Dry-run / confirmation (IMPORTANT + security-sensitive)
- Must **preview all pending changes** and ask for confirmation before
  executing.
- Preview shows, per user: **the password in clear text** and the groups to
  be joined — then moves to the **next user** (sequential, one at a time
  entry).
- After confirming an action, produce a **temporary text file** (e.g.
  `ad-tools-created-users-YYYYMMDD-HHMM.txt`) that records only:
  `username <name.surname>` and `password <cleartext>`. This is a memory
  record for whoever created users so they can send credentials to the
  new user. Treat it as sensitive (cleartext) and **do not commit it**.
- Security note: clear-text passwords must appear **only on screen** and in
  the aforementioned temporary text file; never in logs, transcripts,
  Git history, or repo files. Consider a show/hide toggle and a warning.

### 7. Rights
- The operator account has rights to modify the AD. Good — no elevation
  design needed beyond their existing delegated/administrative rights.

### 8. To discuss later
- **RESOLVED (Round 2):** tool manages AD only; GLPI reads from AD.
- Remaining items still open (see Open questions above).

## Round 2 decisions (Richard, 2026-10-15)

### Edition: Windows PowerShell 5.1 (decided)
Target **Windows PowerShell 5.1** for maximum compatibility with the client.
Consequences:
- This project takes a **scoped exception** to the repo's "PS7 only" rule.
- `AdManager.ps1` drops `#Requires -Version 7` and must be 5.1-syntax clean.
- PSScriptAnalyzer should enforce 5.1-compatible syntax for this project
  (proposal: a project-local settings file with `PSUseCompatibleSyntax`
  TargetVersions `@('5.1')`, see "Tooling follow-ups" below).
- Client check for `pwsh` 7 is now moot; 5.1 it is.

### UI stack for 5.1 (decided direction)
**WPF** — native to 5.1 / .NET Framework 4.8, and we already verified
`Apartment: STA` + `WPF load: OK` on the client.

Windows-11 "Fluent" look — options, verified against upstream docs:
| Option | net48 support | Notes |
|---|---|---|
| **Hand-rolled Fluent XAML** (recommended) | ✅ n/a | Zero third-party DLLs to ship; rounded corners, Segoe UI, accent colour, Fluent spacing done by hand. Best for "maximum compatibility" and clean deployment. More styling work. |
| MahApps.Metro 3.0 | ✅ net462 (≥4.6.2) | Ready-made Win11 window chrome (caption buttons, snap layouts, backdrops). **3.0 is a release candidate**; ships ControlzEx + MahApps DLLs. |
| ModernWPF | ⚠️ net462 assets exist | 1.x is preview, 0.9.x frozen/unsupported. Single-ish DLL. |

Decision: **WPF + hand-rolled Fluent styles, no external theme library**, to
keep deployment dependency-free. Revisit MahApps.Metro 3.0 only if the
hand-rolled chrome proves too much work.

### Scope: AD only (GLPI reads AD)
Richard: "GLPI reads the AD." So the tool **manages Active Directory only**;
it does not write to LDAP/GLPI. GLPI authenticates against AD by its own
mechanism. This closes open question 7 and much of §8.

### Password generation (spec)
- **Length: 10 characters**, fixed.
- Structure: `<Word><digits><special>` where
  - `<Word>` = a French menuiserie word, **first letter upper, rest lower**,
  - `<digits>` = random digits, count = `10 − len(word) − 1`,
  - `<special>` = one trailing special character.
- So: len 5 word → 4 digits; len 7 word → 2 digits (always ≥2 digits).
- Special set (proposed): `! # $ % & * ? @ + = -`
- Accents are **stripped** for password use (é→e, ê/è→e, â→a, ç→c, ô→o,
  û→u, œ→oe) so the character set is ASCII-safe on any keyboard.
- Examples: `Porte8402!` · `Chassis37#` · `Bois12345?`
- Satisfies typical AD complexity (upper + lower + digit + special).
- Open: does the 3-month rotation get *set by the tool* (`-PasswordNeverExpires $false`
  / PSO) or is it already domain policy? Assumption: **domain policy**; tool
  only sets `-ChangePasswordAtLogon $false`.
